# MR 정렬 실패: 입력과 실행 버전 진단

## 해결 상태

이 변경은 정렬 알고리즘 수정이 아니라, 실제 iPhone 실패와 별도 로컬 재현 결과를 대조하기 위한 진단 보강이다. 사용자에게 받은 파일 쌍은 기존 main 엔진과 AAC를 지원하는 데스크톱 Chromium의 실제 비교 Worker에서 정렬에 성공했다. 기존 iPhone 진단의 녹음 길이와 첨부 파일의 디코딩 길이가 달라 같은 입력·디코딩·엔진인지 아직 확정할 수 없다. 등록 MR은 3개라는 확인을 받았으므로 자동 선택의 3개 제한을 이번 원인으로 판단하지 않는다.

원본 파일, MR, 기존 분석 및 DB는 변경하지 않았다. 실제 음원은 별도 비공개 임시 경로에서 읽기 전용 수동 검증에만 사용했다. 저장소·CI·스크린샷·보고서에 음원, 파일명, 미디어 식별자, 서명 URL을 포함하지 않는다.

## 변경 내용

기존 `format:2` 진단에 선택 필드를 추가한다. 녹음과 각 MR 시도에 실제 읽은 바이트 수, 디코딩된 sample rate·채널 수·프레임 수·길이를 기록한다. `decodeAudioData`가 입력 버퍼를 분리하기 전에 바이트 수를 확보한다. MR PCM 캐시에도 당시 입력 정보를 함께 보관해 두 번째 녹음과 재진입에서 정보가 사라지지 않게 한다.

분석 결과의 `runtime`에는 측정 당시 페이지·Worker·사용한 MR 모듈의 숫자 리비전을 기록한다. MR 모듈을 실행하지 않았으면 해당 리비전은 null이다. 페이지 8 / 비교 Worker 8 / MR 모듈 5이며 MR 계산 로직은 변경하지 않는다. 실제 Worker의 응답으로 Worker 리비전을 받아 이전 Worker가 응답하면 임의로 최신이라고 표시하지 않는다.

기기 결과 캐시에서도 당시 정보를 복원한다. 예전 결과에 새 정보를 덧씌우거나 재측정을 자동 실행하지 않는다. 이전 결과의 `input`과 `runtime`은 null이다. 알고리즘·문턱값·MR 선택 순서·결과 캐시 서명 `cancel-v5`·모델 `vp-0.2`는 유지한다.

## 재현·회귀 검증

- 먼저 새 입력 정보가 진단에서 누락되는 실패 테스트를 작성하고 실패를 확인했다.
- 합성 데이터로 녹음/MR 바이트 수·디코딩 정보·실행 리비전, 두 녹음이 공유하는 MR 캐시, 기기 결과 캐시 복원, 식별자·음원·임의 필드 배제, 예전 결과 및 잘못된 값 처리를 검증한다.
- 기존 파일 읽기·재시도·취소·정렬·상쇄·분석 결과 보존 테스트를 함께 실행한다. 실행 수와 최종 결과는 PR Checks에 기록한다.
- 실제 파일 쌍을 별도 로컬 Chromium에서 읽어 현재 Worker의 정렬 성공을 확인한다. 이 결과를 실제 iPhone 성공으로 취급하지 않는다.

화면 배치와 문구 변경이 없어 시각적 전후 차이는 없다. 기존 합성 화면 증거는 [자동 시작점 정렬 검토](MR_AUTO_START_2026-11-17.md)에 있다.

## 배포 후 확인 및 남은 제약

새 페이지에서 같은 기준·비교를 선택해 **다시 재기**를 한 번 실행한 뒤 **진단 파일**을 내보낸다. 재측정하지 않은 예전 결과의 입력 정보는 알 수 없다. 새 진단의 입력 크기·길이·리비전을 첨부 파일의 로컬 검증과 대조해 파일 선택/디코딩/실행 코드의 차이를 좁힌다. 바이트 수가 같다는 사실만으로 파일 내용까지 동일하다고 확정하지 않는다.

실제 iPhone Safari/PWA 디코딩·정렬 및 음질 청취는 미검증이다. 이 진단 배포만으로 사용자 실패가 해결됐다고 보고하지 않는다. 데스크톱 Chromium의 AAC 디코딩 지원은 사용한 실행 파일에 따라 다르며, AAC 미지원 테스트 브라우저의 디코딩 실패를 앱 결함이나 원본 손상으로 취급하지 않는다.
