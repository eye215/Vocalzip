# Phase 06-A: 완료된 R2 업로드의 보관함 연결 복구

2026-11-08. UI/레이아웃·운영 DB·Worker·기존 미디어 변경 없이 기존 업로드/재시도에 연결한다.

## 범위

R2에서 key/size/etag 완료 응답을 받은 뒤 vocal_media 저장/확인만 실패한 경우를 복구한다. 새 파일을 다시 선택하지 않아도 로그인·온라인 복귀·화면 복귀 때 보관함 연결을 재시도한다. 같은 ID의 가져오기 재시도도 같은 경로를 사용한다.

- media-upload-recovery.js: 계정+미디어 ID별 독립 localStorage 영수증. 원본명·곡·날짜·길이·출처 등 확정할 metadata와 key/size/etag를 함께 보존한다.
- cloud-sync.js: metadata 쓰기 전에 영수증 저장. 기존 전역 업로드 잠금 안에서 복구하고, 기존 PK 기준 ignoreDuplicates INSERT만 허용한다. 기존 행의 이름·곡·메모·날짜를 덮어쓰지 않는다.
- r2-storage.js: 원본 확인 요청에도 등록 세션 프로토콜 헤더를 보낸다.
- index.html / legacy.html: 저장 모듈 스크립트 추가와 캐시 버전만 변경한다. 화면 구성/스타일 변경 없음.

## 복구 조건

1. 검증된 현재 계정/세션과 원래 계정 저장소가 일치해야 한다.
2. 서버·기기의 삭제 표식에 ID가 있으면 연결하지 않는다. 삭제 기록을 확인할 수 없어도 중단한다.
3. 같은 소유자의 동일 media ID 경로이며 R2에서 확인한 크기와 강한 etag가 완료 영수증과 같아야 한다. 크기만 같은 다른 객체는 거부한다.
4. 기존 보관함 행이 다른 객체를 가리키면 자동 수정하지 않는다. 원래 객체를 가리키면 다른 기기의 최신 편집값을 그대로 반환한다.
5. INSERT 응답이 끊겨도 행을 다시 조회해 확인한다. 확인 실패·권한/네트워크 오류는 영수증을 보존한다.
6. 실제 행을 확인한 뒤 해당 영수증만 제거한다. 제거 실패는 다음 재시도에서 확인하며 이미 저장된 행을 실패로 바꾸지 않는다.

재시도는 bytes 업로드/원본 다운로드/객체 삭제를 하지 않는다. 검증은 기존 Range 1바이트 API를 사용한다.
계정별 1,000개/직렬화 크기 약 4MiB를 기술적 안전 상한으로 두고, 한도·손상·미래 포맷을 만나도 기존 영수증을 자동 정리하지 않는다.
영수증에는 파일 blob·토큰·서명 URL이 없다. 기존 간략 orphan 진단 정보만 남은 파일은 메타데이터를 추측하여 일괄 복구하지 않는다.

개발 인터페이스: window.vzipRecoverMediaUploads(id?) → [{id,status,metadata?/code?}]. id 생략 시 본인 영수증만 대상으로 한다. 이 함수는 사용자 파일 내용을 출력하는 로깅을 추가하지 않는다.

## 남은 범위와 검증 한계

- multipart complete 응답 자체가 유실되거나, 완료 응답 직후 영수증 저장 전 탭이 강제 종료되면 확정 영수증이 없다. 이 경우에는 아직 자동 복구하지 않는다. Worker 작업 원장/업로드 세대 fencing이 다음 06-B다.
- 전송 중인 part를 새로고침 후 이어 올리기, 대용량 원본의 로컬 보존·저장공간 압박, 기존 고아 파일 대조는 별도다.
- 동일 media ID의 다른 기기 업로드에 대한 R2 객체 덮어쓰기 방지, 삭제와 복구의 서버 원자적 조정은 별도다. 삭제 표식을 매 단계 재확인해도 HTTP 요청 사이의 경쟁 전체를 제거하지는 못한다. 이 변경만으로 즉시 삭제/미디어 Phase 완료를 선언하지 않는다.
- 기기 localStorage 자체가 삭제/유실되면 해당 영수증도 없다. 서버 영수증 원장 구축 전까지 기기 간 복구를 보장하지 않는다.
- Node 가짜 저장소/전송 어댑터 시험과 Playwright의 모의 Supabase/R2 시험이다. 실제 Supabase·R2/iPhone/PWA·배경 지속 업로드의 검증 결과로 확대하지 않는다.
