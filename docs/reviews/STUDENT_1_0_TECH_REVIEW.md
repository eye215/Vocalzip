## 1. 결론과 검토 경계

**학생 1.0의 기록·학습·보관 기능은 기술적으로 구현 가능한 범위다. 최신 제품 결정서로 영상 범위·직접 삭제·AI 실행 방식·2.0 공유 방향은 확정됐다. 남은 주요 위험은 그 정책을 지킬 동기화·복구·미디어 권한·AI 평가·iOS 구현·사용량 계약이다. 현재 자료만으로 개발 규모나 출시 일정을 확정하기는 어렵다.** 학생 전체 기능을 출시한다는 목표는 유지하고, 불확실한 요구사항을 검증 가능한 계약으로 바꾸는 것이 우선이다.

이번 검토는 지정된 6개 문서, CLAUDE.md의 추가 필독 자료, 최신 제품 결정서를 읽은 **설계 검토**다. Claude의 Phase 01 코드·운영 전수 조사, 기능 재현, DB 조회, 미디어 점검을 중복 수행하지 않았다. 저장소 트리는 작업 지침과 산출물 경로 확인에만 사용했다. 실행 가능한 SQL·기능 코드는 작성하지 않는다.

판정 표기:

- **구현 가능:** 알려진 기술로 요구를 충족할 수 있다는 설계 판단. 현행 구현 또는 테스트 통과를 뜻하지 않는다.
- **조건부 가능:** 지원 환경·권한·정확도·제품 정책을 확정하고 검증해야 한다.
- **문서상 설명:** 참고 문서가 기술한 과거 상태. 현재 main 또는 운영 상태의 확정 근거가 아니다.
- **Phase 01 대조 대기:** Claude의 파일·커밋·테스트 근거로 판단을 갱신해야 한다.

특히 README와 11월 4일 운영 문서는 이후 변경을 모두 반영했다고 보장할 수 없다. 그 문서의 테스트 건수를 이번 검토의 통과 건수로 재사용하지 않는다. **이번 작업에서 앱 테스트·iPhone 테스트·운영 검증은 실행하지 않았다.**

## 3. 기존 코드 재사용 가능성

다음은 [v6 구조 문서](../UIUX_v6_개편_2026-11-04.md), [README](../../README.md), [레슨 연동 계약](../레슨데이터_연동계약.md)이 설명한 **재사용 후보**다. 이번 검토에서는 해당 서비스 코드를 다시 감사하지 않았다.

| 문서가 지목한 경계 | 재사용할 자산 | 바로 재사용한다고 가정하면 안 되는 부분 |
|---|---|---|
| `app/core.js` | ID·날짜·기록 접근, 라우팅·시트·확인 UI | localStorage 전체 문서 쓰기를 미래 협업 DB 계약으로 그대로 확대 |
| `app/media.js` | 기존 Blob/bytes 읽기, 통합 목록, 미디어 ID, 재생 UI | 브라우저 녹음·저장 동작을 iOS 앱의 백그라운드 보장으로 간주 |
| `app/views-main.js`, `app/views-lessons.js`, `app/views-more.js` | 곡·연습·개인 레슨·숙제 폼, 기존 사용자 흐름 | DOM 직접 결합·전역 상태를 새 기능마다 중복 확장 |
| `cloud-sync.js` | 기존 로그인 데이터 읽기, 병합 호환, 업로드 연결 | 단말 시각 우선 병합만으로 동시 쓰기 안전성을 보장 |
| `chunk-media-core.js`, `chunk-media.js`, `share-worker.js` | 기존 분할 객체 명세·바이트 범위 재생·호환 테스트 | 전송 청크, 저장 청크, R2 multipart part를 같은 개념으로 취급 |
| `billing/` 및 레슨 계약 | ID·날짜·상태 읽기와 별도 원장 보존 | 학생 개인 기록·선생님 수납·앱 구독을 하나의 결제로 통합 |
| `legacy.html`, 기존 테스트 | 과거 데이터 읽기와 회귀 기준 | 이전 완료 전에 제거하거나 옛 클라이언트의 쓰기 영향을 무시 |

권장 변경 방향은 **기존 저장 형식을 읽는 어댑터 → 도메인별 저장 인터페이스 → 화면의 점진적 연결**이다. 전면 재작성·프레임워크 전환을 선행 조건으로 삼지 않는다. 새 DB 테이블 수나 프레임워크도 Phase 01 근거 없이 확정하지 않는다.

재사용의 승인 조건은 “파일이 있다”가 아니라 다음 네 가지다.

1. 현재 main의 코드 경로와 호출자가 확인됨.
2. 과거 ID·날짜·삭제·미디어 형식 fixture를 읽고 의미가 보존됨.
3. 변경 경계의 자동 회귀 검사가 통과함.
4. 녹음·저장·동기화처럼 운영 의존 기능은 실제 기기·계정 검증이 별도로 기록됨.

## 5. 추천 기술 구조와 데이터 계약

### 5.1 추천 구조: 계약을 공유하고 저장소·플랫폼을 분리

```text
웹/PWA 화면                 iOS 앱 화면(재사용 범위는 Phase 02 결정)
      └──────── 도메인 서비스·입력 검증·동일 ID 계약 ────────┘
                ├─ 기기 저장 어댑터 + 영속 작업 대기열
                ├─ 인증·버전 검사 API → Supabase Auth/Postgres
                └─ 미디어 권한 API → 현행 저장소 / 비공개 R2
                                         └─ 비동기 변환·AI 작업
```

- **Supabase:** 인증, 사용자별 구조화 기록, 참조·소유권·공유 권한, 작업 상태, 사용량·구독 권한의 서버 원장.
- **R2:** 오디오·영상·PDF·파생 파일의 바이트. DB 소유권 판단이나 구독 원장을 대신하지 않는다.
- **기기:** 즉시 기록·재생·오프라인 작업의 지속 저장. 계정별 기준 원천은 클라우드이나, 승인 이전 로컬 변경·미업로드 음원은 버리지 않고 복구 가능하게 보존한다.
- **서버 작업 실행기:** 변환·전사·분석. 저장 성공과 독립적으로 실패·재시도한다. 기존 실행기 재사용 가능성은 Phase 01 결과로 결정한다.
- **화면:** 저장 방식이나 R2 객체 경로 대신 도메인 ID와 명확한 상태를 사용한다.

모든 학생 엔터티를 즉시 테이블로 분리할 필요는 없다. 다만 권한·사용량·작업·동시 수정 제어처럼 서버가 권위 있는 결정을 내려야 하는 계약은 개인 JSON 전체 덮어쓰기와 구별한다. 협업 데이터에 개인 payload 전체 공유를 사용하지 않는다.

### 5.2 학생 1.0에서 반드시 정할 최소 계약

아래 필드명은 개념 예시이며 운영 스키마 확정안이 아니다.

| 계약 | 필수 의미 |
|---|---|
| 식별자·소유권 | 변경하지 않는 기존 ID, `owner_id`, 객체 유형, 필요 시 `legacy_id`·원천. 신규 UUID 강제를 위해 기존 문자열 ID를 버리지 않음 |
| 수정·삭제 | 서버 revision, 생성·수정 시각, 삭제 표식과 보존 기간, 스키마 버전. 단말 시각을 유일한 충돌 판정 기준으로 쓰지 않음 |
| 로컬 작업 | `operation_id`, 사용자·기기 범위, 대상 ID, 기준 revision, 변경 내용, 승인·실패·충돌 상태 |
| 미디어 | 논리 media ID, 소유자, 형식·길이·크기·검증 정보, 저장 provider와 객체 참조. 내부 파생 관계는 유지하되 소유자가 선택한 영상/음원만 사용자 보관함 항목으로 생성 |
| 날짜 | 날짜만 있는 기록의 local date, 시각이 알려진 경우 instant와 시간대, 출처·정밀도·수동 수정값. 알 수 없는 시간대를 생성하지 않음 |
| 관계 | 연습↔미디어, 레슨↔곡/미디어, 공연↔곡을 독립 연결로 표현. 소유권·접근권을 참조할 때마다 검증 |
| 전사·분석 | 입력 media revision/hash, 구간·시간 단위, 처리기·모델·파라미터 버전, 근거·신뢰도·실패 이유·수정 이력 |
| 출처 | 학생 메모, 학생이 옮긴 교사 발언, 인증 교사 작성, AI 제안을 구별. 입력자와 내용의 대상은 다름 |
| 임포트·복원 | 작업 ID, 원천 식별자, 생성/연결/건너뜀/실패, 변경 전 값, 검증 결과. 나중에 편집된 데이터를 무조건 되돌리지 않음 |
| 사용량 | 저장 예약·확정·해제와 AI 예약·소비·환급을 멱등 거래로 기록. 표시용 카운터는 원장 대조 가능 |

통계는 날짜·단위를 명시한다. 연습 시간을 여러 곡에 각각 전량 더하지 않는다. 녹음 수·전체 녹음 길이는 미연결 녹음도 포함하며 연습 시간에는 자동 합산하지 않는다. 파일 수는 논리 media ID 기준이며 분할 객체·파생본·다중 연결을 중복 계산하지 않는다. 날짜가 같은 레슨·파일은 중복 판정 근거가 아니다. 해시는 후보 검출에 쓰되 다른 사용자의 파일 존재를 알려주지 않는다.

### 5.3 학생·선생님 확장 시 가장 중요한 경계

1. **학생 개인 레슨 기록과 선생님이 운영하는 실제 수업 회차는 별도 생명주기다.** 미래의 `lessons`라는 같은 이름으로 개인 메모를 공동 수업에 합치면 비공개 메모가 노출될 수 있다. 개인 기록에 선택적 `session_id`를 연결하는 방식 등을 Phase 03에서 비교한다. 기존 개인 ID는 유지한다.
2. **소유자·작성자·대상 학생·읽을 수 있는 사람을 분리한다.** `user_id` 하나로 모두 표현하지 않는다. 역할 전환은 UI 상태이고 데이터 접근 허가가 아니다.
3. **곡은 우선 사용자 소유 레퍼토리다.** 같은 제목을 전역 곡으로 합치지 않는다. 나중의 공통 작품 카탈로그는 선택적 별도 참조로 연결하고, 개인 키·메모·가사·녹음은 소유 범위를 유지한다.
4. **그룹 멤버십 이력과 수업별 참여자 스냅샷을 분리한다.** 새 멤버가 과거 개인 피드백을 보거나 탈퇴 때문에 출석·정산 기록이 사라져서는 안 된다. 공동 강사도 수업·학생별 권한이 필요하다.
5. **숙제 정의/배포, 수신 학생, 수행 기록, 최종 완료 상태를 분리할 확장점을 둔다.** 학생 1.0에서는 개인 숙제로 구현하되, 2.0에서 과거 수행 이력을 공동 수정 필드로 덮어쓰지 않는다.
6. **2.0의 범위형 공유와 승인형 수정을 구체화한다.** 선생님별 전체 보관함(기존·미래 자료)/제출 자료 권한과 파일별 제외를 별도로 저장하고 제외가 우선하도록 한다. 연결 해제·범위 축소·휴지통은 읽기 권한에 즉시 반영하는 계약이 필요하다. 결제·계정·비공개 메모를 전체 보관함 권한에 포함하지 않는다. 수정 제안에는 원본 revision·제안 diff·제안자·학생 승인/거절·감사 이력을 남기고, 승인 시 원본이 달라졌으면 다시 확인한다. 선생님이 직접 덮어쓰는 권한으로 구현하지 않는다.
7. **연결 해제 후 보존과 접근을 따로 결정한다.** 교사가 쓴 피드백의 학생 열람·내보내기, 교사 탈퇴, 공동 녹음의 동의·소유권, 기존 다운로드 사본의 한계를 정책으로 정한다.
8. **원장 세 가지를 구분한다.** 학생 개인 레슨비 기록, 선생님 수강권·수납 거래, 앱 구독은 별도. 2.0의 차감은 학생·회차·거래 식별자로 중복 방지하고 정정은 역거래로 남긴다.
9. **1.0에서 미래 테이블 전체를 만들지 않는다.** 소유권·출처·관계·버전 계약만 확보하고 2.0 확장 스키마는 실제 협업 요구 확정 후 작성한다.

### 5.4 동기화·이전 계약

- 서버 승인 전 로컬 작업을 지우지 않는 outbox를 권장한다. 서버는 작업 ID 중복을 흡수하고 기준 revision이 다르면 충돌을 반환한다.
- 서로 다른 레코드 수정과 같은 레코드 수정은 별도 테스트다. 같은 메모의 동시 수정은 양쪽 내용을 보존하고 정책에 따라 사용자 선택 또는 안전한 병합을 한다.
- 삭제 표식이 너무 일찍 사라지면 오래 오프라인이던 기기가 삭제 데이터를 되살릴 수 있다. 보존 기간, 오래된 클라이언트의 재동기화, 최소 지원 버전을 함께 정한다.
- JSON→신규 구조 전환 시 한 엔터티의 권위 있는 쓰기 위치를 한 번에 하나로 정한다. 과도기 이중 쓰기는 재시도·대조·복구 원장이 없으면 채택하지 않는다.
- 옛 앱이 모르는 필드를 버리는지 확인하고, 안전한 호환 읽기/쓰기를 입증하지 못하면 해당 버전의 쓰기를 제한하는 전환 계획이 필요하다.
- 웹 origin의 localStorage/IndexedDB가 iOS 앱으로 자동 이전된다고 가정하지 않는다. 클라우드 검증 또는 사용자 승인 내보내기/가져오기 경로로 이전한다.
- DB 백업, 미디어 객체 목록, 실제 파일 복사본은 서로 다르다. 목록만으로 삭제된 파일을 복구할 수 없으므로 복구용 바이트 확보·복원 시험을 별도 요구한다.

## 6. Supabase와 Cloudflare R2 연동 위험

**Supabase의 RLS는 R2 객체에 자동 적용되지 않으며, 두 저장소에 걸친 하나의 원자적 트랜잭션도 가정할 수 없다.** 미디어 권한 API와 복구 가능한 작업 상태가 필요하다.

### 6.1 권장 업로드 상태 흐름

`local_saved → reserved → uploading → verifying → ready`

취소·실패·재시도는 별도 상태로 관리하고, 기기 저장 상태와 서버 업로드 상태를 하나의 성공 플래그로 합치지 않는다.

1. 인증된 사용자와 media ID로 작업을 생성한다. 예상 용량을 원자적으로 예약하고 반복 요청에는 같은 작업을 반환한다.
2. 서버가 결정한 사용자 범위의 객체 키와 제한된 업로드 권한을 발급한다. 클라이언트가 다른 사용자의 경로나 완료 상태를 지정하지 못한다.
3. 파일/part 상태를 지속 저장한다. 재시작 시 서버와 대조하고 원본 재선택이 필요하면 같은 파일인지 검증한다.
4. 서버가 실제 존재·크기·필요한 무결성을 확인한 뒤 ready와 사용량 확정을 멱등 처리한다. multipart ETag를 원본 파일 전체 해시로 간주하지 않는다.
5. 객체만 있고 DB 확정이 실패했거나, DB 작업만 있고 업로드가 실패한 경우 복구·정리 대상으로 남긴다. 객체 존재만으로 성공 또는 자동 삭제를 결정하지 않는다.

현행의 독립 분할 저장 객체와 R2 multipart는 다르다. 기존 분할 매니페스트를 읽는 어댑터를 유지하고, 새 업로드 전략을 선택한다. 실제 최대 크기·동시 전송·임시 공간·압축 부담은 Phase 06에서 실기기로 검증한다.

### 6.2 접근·재생·공유

- Worker/API는 JWT의 서명·발급자·대상·만료와 대상 미디어의 현재 소유권/권한을 검증한다. 요청의 owner 값이나 CORS를 인증으로 사용하지 않는다.
- RLS는 소유 행의 읽기뿐 아니라 삽입·수정 시 소유자 변경, 관계 테이블, RPC·뷰·관리자 경로까지 검증한다. 관리자/service-role 권한을 쓰는 실행기는 별도 소유권 검사가 필요하다. [Supabase RLS][E3]
- S3 presigned URL은 가진 사람이 만료 전 사용할 수 있는 bearer 권한이다. DB 공유 회수만으로 이미 발급된 URL이 즉시 무효화된다고 약속하면 안 된다. 회수 허용 지연을 정하거나 매 요청에 현재 권한을 검사하는 경로를 선택한다. R2 S3 presigned URL을 custom domain URL로 단순 치환하지 않는다. [R2 서명 URL][E2]
- Range/206·HEAD·탐색·URL 갱신·중간 만료·캐시가 같은 권한 정책을 따라야 한다. 사용자별 서비스 워커/캐시 분리와 로그아웃 시 재생 중지·접근 차단이 필요하다.
- 1.0의 개별 공유는 선택 파일만 허용하며 곡의 모든 자료·전사·레슨 메모로 권한을 확대하지 않는다. 2.0 전체 보관함 권한은 별도 동의 계약으로 구현한다. 공유 링크 토큰과 서명 URL은 로그·분석 이벤트에서 제거한다.
- 다운로드·이미 수신된 바이트까지 회수할 수 있다고 표시하지 않는다.

### 6.3 용량·삭제·미디어 이전

- 원본·추출 음원·720p 영상·AI 파생본·실패 part 중 무엇을 사용자 한도에 포함하는지 결정한다. 공유는 별도 원본 과금을 만들지 않는다.
- 두 기기의 동시 업로드가 각각 남은 용량을 통과하지 않도록 서버 예약을 사용하고 만료 예약·실제 객체·원장을 대조한다.
- 관계 삭제, 기기 캐시 정리, 클라우드 원본 삭제, 계정 탈퇴를 다른 명령으로 다룬다. 참조 수만으로 공유 파일 삭제 권한을 정하지 않는다.
- 기존 저장소→R2 전환이 필요하다면 복사→크기/해시·재생 검증→참조 전환→관찰→별도 승인된 정리 순서다. 이번 검토는 이전을 실행하거나 승인하지 않는다.
- **직접 삭제:** 삭제 시점부터 30일 복구가 확정 정책이다. 서버 기준 `deleted_at`·`purge_after`, 원래 연결 스냅샷, 복원/정리 작업 ID를 정의한다. 휴지통 기간에는 실제 바이트를 유지하며 공유 재생은 차단한다. 30일 정리 직전 복원·참조 상태를 재검사하고 복원과 영구 삭제가 동시에 성공하지 않도록 원자적으로 작업을 확보한다. DB/객체의 부분 삭제는 재시도 원장으로 추적한다. 정산 원장은 별도로 유지하고 복원 시 재차 차감하지 않는다.
- 30일 복원 시 기존 ID·소유권·관계를 유지하되 이미 삭제된 외부 공유 권한을 자동 부활시키지 않는다. 연관 곡/레슨이 별도로 삭제되었다면 복원 가능한 관계와 불가능한 관계를 보고한다. 휴지통 용량 과금과 백업 사본의 영구 삭제 의미는 추가 결정이 필요하다.
- **구독 만료:** 유효기간 종료부터 29일 유예·30일 차 초과 정리 가능성 및 반복 고지는 확정 방향이다. 실제 초과 파일 자동 영구 삭제는 법률·약관·복구 검증과 별도 승인 전 활성화하지 않는다. 직접 삭제와 별도 시계·작업 유형을 사용한다.
- 종료 7일 전/종료 당일/유예 14·25·29일/정리 결과 고지를 기본 일정으로 설계한다. 재구독·복원·발송 실패·반송·중복 이벤트를 처리하고 재구독 확인 시 정리를 중단한다. 해지 버튼 클릭을 만료일로 쓰지 않는다.

### 7.1 가능 범위와 한계

### 7.2 AI 출시 검증 계획 제안 — 미실행

1. 동의를 받은 평가 자료를 별도 관리한다. 한국어·영어 가사, 말/노래/반주/중창, 음역·키 변경, 잡음·잔향, 무음, 여러 곡이 든 파일을 나눈다. 원본을 GitHub에 올리지 않는다.
2. 학습·참조 자료와 평가 자료를 분리하고, 같은 녹음의 파생본이나 같은 연주가 양쪽에 섞이지 않도록 한다.
3. 전사는 CER/WER와 시간 정렬 오차·무음 환각 빈도, 곡 추천은 top-k recall·잘못 승인할 위험·판단 보류율, 음높이는 cents 오차·옥타브 오류·유성 구간 판정, 박자는 전문가 기준 onset 오차·실패 조건을 평가한다.
4. 지표·녹음 조건별 출시 임계값과 지원하지 않는 조건을 실험 전에 정한다. 이 문서는 측정하지 않은 정확도 숫자를 약속하지 않는다.
5. 원본 재생 위치와 결과 근거를 연결한다. 저신뢰·분석 불가를 정상 결과로 처리하고 사용자 수정은 원 결과와 별도로 보존한다.
6. 모델/파라미터 버전이 바뀐 결과를 같은 성장 점수 축에 무조건 이어 붙이지 않는다. 비교 가능성 검증 또는 재분석 정책이 필요하다.

### 7.3 작업·비용·개인정보

- 무료 기기 기초 분석·규칙 추천은 자동 가능하다. 결정서가 지목한 `app/practice-tips.js`는 재사용 후보이며 최신 구현·검증 상태는 Phase 01에 맡긴다.
- **유료 서버 전사·정밀 분석·성장 리포트는 사용자 요청이 있어야 한다.** 원본 저장 완료·AI 동의·서버 상품 권한·한도 확인 뒤 작업을 요청한다. 저장 성공은 AI 성공에 의존하지 않는다.
- 묶음 요청 ID와 파일별 분석 번들 ID를 구분한다. 일간 요청 수·월간 실제 파일 수·분·파일 길이·동시 실행·전체 예산을 함께 예약하고 한도 하나라도 초과하면 신규 고비용 작업을 제한한다. 전사+분석 번들의 파일 수를 중복 차감하지 않는다.
- 날짜/월 경계의 기준 시간대, 분 단위 반올림, 재분석 과금, 부분 성공·취소 환급, 가안 변경 시 기존 가입자 적용을 결정해야 한다. 파일 길이는 클라이언트 신고만 신뢰하지 않고 검증한다. 대기 작업의 예산도 예약해 동시 요청으로 전체 예산을 넘기는 상황을 줄인다.
- 결정서의 시험 예산 알림·제한은 녹음·저장·재생·무료 추천을 막아서는 안 된다. 상용 요금제의 약속된 이용량과 전체 예산 제한이 충돌할 때의 안내·보상/권한 정책을 출시 전 정한다.
- 입력 revision·분석 유형·모델/설정으로 작업 중복을 막는다. 실행 임대·heartbeat·재시도 상한·취소를 정의하고, 취소 후 늦게 도착한 결과가 삭제된 기록을 부활시키지 않도록 한다.
- 비용은 파일 개수보다 분석 길이·재시도·변환 비용과 관련된다. 예상 소비 안내와 예약/정산/실패 환급 정책을 정한다.
- 전사·학생 메모는 추천 모델의 입력 데이터이며 시스템 지시로 실행하지 않는다. AI 결과는 검증된 구조로 받아 사용자 승인 없이 권한·원본·곡 연결을 수정하지 못하게 한다.
- 동의에 제공자·전송 범위·보관 기간·재학습 사용 여부·철회 효과를 포함한다. 레슨 녹음에는 타인의 음성이 포함될 수 있다.
- 멜로디 기반 매칭은 별도 평가가 필요한 확장 후보다. AR YouTube 링크는 참고 자료이며 링크 등록만으로 분석 가능한 오디오가 생기지 않는다. 적법한 접근·구간·버전·분석 입력이 확보되기 전 1.0 정확도 향상의 전제로 삼지 않는다.

## 8. iOS 정식 출시 시 필요한 네이티브 기능

**권장 후보는 기존 도메인·UI를 최대한 재사용하는 하이브리드 셸 + 네이티브 미디어/파일/인증/결제 연결이다. 확정 선택은 아니다.** Phase 02에서 녹음·중단 복구·업로드·기존 데이터 접근을 실물 iPhone으로 먼저 검증하고, 브리지 복잡도와 네이티브 화면 개발 비용을 비교한다. 웹뷰로 감싸는 것만으로 OPS-01/IOS-01이 충족되지 않는다.

| 기능 | 네이티브 검토 범위 | 실기기 인수 조건 |
|---|---|---|
| 녹음·재생 | AVAudioSession/AVFoundation, 실제 파일 지속 저장, 권한 설명 | 잠금, 전화·Siri, 이어폰/Bluetooth 연결 변경, 일시정지, 저장 공간 부족, 앱 재실행 |
| 업로드 | 파일 기반 background URLSession과 영속 작업 매핑 | 중단·서명 만료·재시작·재선택·용량 예약 복구. 강제 종료 후 무조건 자동 전송 보장 금지 |
| 파일 가져오기 | 문서 선택기, iCloud 파일 다운로드, 보안 범위 접근 | 다중 파일, 접근 만료, 파일 변경, 대용량 임시 공간, MOV/HEVC 음성 트랙 |
| 공유 | 내보내기 공유 시트; 앱으로 받기는 Share Extension 등 별도 구현 | 본 앱이 닫힌 상태에서 수신, 중복 수신, 계정 미확정 파일의 안전한 보류 |
| 사진/영상 | 소유자 전용 영상의 시스템 선택기·기기 압축/추출 | 서버 허용 계정·600초·형식 검증, 일반 계정 차단, iCloud 대기, 저장 형식 택1·중복 생성 방지 |
| 로그인 | Apple 인증, OAuth 복귀·딥링크, 안전한 자격 증명 저장 | Apple·카카오 계정 중복, 세션 만료, 앱 재설치, 재인증·연결 해제 |
| 구독 | StoreKit 및 서버 거래 검증·알림 처리 | 구매 대기·취소·복원·환불·다른 앱 계정에 복원·순서 뒤바뀐 이벤트 |
| 알림 | 필요 시 로컬 알림/APNs, 권한·예약 상태 | 거부, 시간대 변경, 레슨 취소, 중복 알림 |
| 저장·복구 | 앱 파일 저장·보호, 계정별 메타데이터/대기열, 웹 데이터 이전 | 로그아웃·계정 변경 시 노출 방지와 미전송 파일 보존을 동시에 확인 |

Apple의 background URLSession은 파일 기반 업로드를 요구하며, 사용자 강제 종료는 별도 제약이다. PWA의 열린 페이지 재시도를 이 보장으로 대신하지 않는다. [Apple 백그라운드 전송][E7] · [background configuration][E8]

정식 출시 정책 확인 항목은 디지털 구독의 결제 경로(스토어·지역별 예외 포함), 소셜 로그인 요건, 앱 내 계정 삭제, 제3자 AI 전송 동의, 공유 콘텐츠 및 외부 음원 이용 범위다. 단순 웹사이트 포장 수준의 앱 심사 위험도 검토한다. 개인정보 표시·SDK 수집 내역·필요한 Privacy Manifest를 실제 구현과 대조한다. 출시 직전 최신 기준을 다시 확인하며 승인 결과를 미리 보장하지 않는다. [Apple 심사 지침 §3.1·4.2·4.8·5.1·5.2][E1]

중요한 선후 관계:

- Phase 19 UX와 21 보안은 전 기간에 적용한다. UI 설계는 먼저 가능하지만 데이터 계약 없는 실제 쓰기 구현은 통합을 기다린다.
- Phase 15와 16은 공통 입력/작업 계약 뒤 병렬 가능하다. Phase 17 전체를 전사의 성공에 묶을 필요는 없지만 사용하는 분석 지표는 검증되어야 한다.
- 동기화·미디어·구독이 함께 수정하는 사용량/권한 계약에는 책임자를 지정한다. 같은 공통 저장 파일을 각 브랜치에서 독립 재설계하지 않는다.
- 병렬 작업은 인터페이스·fixture·변경 소유 파일을 먼저 합의하고 별도 브랜치에서 수행한다. 이번 리뷰는 `docs/reviews/`, Claude의 01 산출물은 `docs/audit/`로 분리한다.

## 10. 우선적으로 해결해야 할 기술적 위험
