# MR 실제 입력의 읽기 전용 운영 진단

사용자 진단 11은 page/Worker 10, MR 모듈 7의 새 측정에서도 기준 녹음이 실패함을 확인한다. 첫 MR의 전체 구간 onset 위치가 21회 반복 검출됐으나 8kHz anchor 검증 통과는 0개다. 이 결과로 캐시나 탐색 후보 수를 원인으로 단정하거나 검증 기준을 낮추지 않는다.

기존 서버 분석 Worker의 R2 읽기 권한으로 정확한 원본과 같은 소유자·곡의 MR 최대 3개를 읽고, 격리된 native Chrome에서 앱의 실제 비교 Worker를 실행하는 수동 운영 진단을 추가한다. 원본의 바이트 수·채널·디코딩 길이·정렬 결과를 iPhone 진단과 대조하기 위한 도구다. 앱과 분석 엔진 코드는 변경하지 않는다.

## 읽기·출력 제한

- 진단의 녹음 바이트 수와 녹음한 달(일·ID 제외)을 바인딩 파라미터로 조회하며 최대 2개, 단일 소유자·곡만 허용한다. 중복 등록 원본은 전체 바이트 SHA-256이 같을 때만 하나로 취급하고 해시는 출력하지 않는다. 모호한 선택은 거절한다.
- SQL은 `BEGIN READ ONLY`, 제한된 SELECT, `ROLLBACK`뿐이다. R2 읽기는 기존 `readMedia`의 소유자 경로 검증을 재사용한다. 원본·분석·계정·스키마를 쓰지 않는다.
- 원본은 프로세스 메모리와 localhost `no-store` 응답으로만 전달한다. 음원 파일·브라우저 trace·스크린샷·다운로드 아티팩트를 만들거나 GitHub에 업로드하지 않는다.
- 출력은 입력 크기·디코딩 정보·엔진 버전·정렬 결과의 허용 필드만 포함한다. 실제 미디어 ID·소유자·곡 이름·R2 key·URL·해시·음원·곡선은 출력하지 않는다. 오류도 고정 코드로 제한한다.
- 운영 진단은 병합된 main에서 수동으로만 실행한다. PR/자동 검사는 합성 데이터만 사용하며 운영 자격 증명을 받지 않는다. 운영 실행은 기존 서버 분석과 같은 범위의 R2/DB 연결을 사용한다.

## 검증과 한계

합성 테스트는 읽기 전용 트랜잭션, 소유자·곡 혼합 거절, 중복 파일 동일성, 크기 제한·오류 비밀값 배제를 확인한다. 별도 합성 녹음/MR을 native Chrome의 실제 Worker로 정렬한다. 원본을 사용하는 실행은 테스트 성공으로 집계하지 않고 별도의 운영 관찰로 기록한다.

서버 Chrome 성공은 실제 iPhone 성공을 의미하지 않는다. 서버도 같은 입력에서 실패하면 그 입력을 기준으로 엔진을 조사하고, 서버만 성공하면 디코딩/플랫폼 차이를 조사한다. 이 도구 자체는 정렬 실패 해결이 아니다. 운영 실행 결과는 PR에 기록한다.

## 추가 관찰

`pitch-guidance` 모드는 기존 음정 엔진의 100Hz 고역 통과 전처리와 전체 음정 가이드를 같은 원본에 적용해 관찰한다. 기존 소리 길 모델의 판정 기준은 그대로 사용한다. 기본 실행 결과를 대체하거나 MR 제거 성공으로 표시하지 않는다. 가이드 곡선과 필터링 음원은 출력하지 않고 검출 일관성·표본 길이·보류 사유만 기록한다.

실제 기준 월을 선택한 운영 실행에서 입력 크기·디코딩 프레임 수가 iPhone 진단과 일치했고, 서버 Chrome도 동일하게 정렬을 거절했다. 최초 reference의 전체 onset 반복 검출은 21회였지만 anchor 검증은 0개였다. 플랫폼이나 열린 페이지 버전만을 원인으로 보지 않는다.

기본 실행이 정렬을 거절하면 원본의 개별 채널과 48kHz/8kHz decode 대안을 최대 4회 추가 관찰한다. 기존 평균 신호와 결과를 대체하지 않고 별도 수치로 남긴다. 최초 reference의 상위 onset 후보 3개에 대해서 기존 fine/local 검사 수치와, 유효한 local 창이 충분할 때 held-out 예측 감소량도 관찰한다. 어느 프로파일도 앱의 승인 기준을 변경하지 않는다. 모든 신호와 residual은 메모리에만 존재한다. 추가 합성 stereo fixture는 평균 신호에서 반주가 상쇄되지만 개별 채널에는 reference가 남는 경우를 검증한다.
