# MR 재분석 대기·메모리 개선 검증

## 재현과 수정

- 여러 녹음의 `MR로 다시 분석`에서 같은 MR을 매번 다운로드·디코딩했다. 배치 실행에만 속하는 Map으로 재사용한다. 최대 24 MiB의 PCM만 보관하고 완료·중단·계정 이탈 시 비운다. 파일 키·크기·수정 정보가 바뀌면 다시 읽고, 실패한 읽기는 캐시하지 않는다. 전송용 복사본을 사용해 worker 전송이 재사용 버퍼를 비우지 않게 한다.
- `반주(MR) 빼는 중…`에는 정렬·차감의 진행률이 오지 않았다. 정렬 후보 및 차감 블록 처리량을 보컬 분석·소리 길 화면의 기존 진행 표시로 전달한다. MR 여러 개와 뒤이은 음성 측정의 진행률도 연결한다.
- 전체 녹음의 STFT 두 개와 전체 길이 Float64 overlap-add 버퍼를 함께 보관했다. 현재·다음 블록의 스펙트럼을 재사용하고, 인접 블록 통계와 512칸 overlap-add 링만 보관한다. 녹음 전체를 끝까지 처리하며 정렬·분리·신뢰도 기준은 유지한다.
- MR URL을 기다리는 중 중단해도 다운로드를 시작하던 문제를 수정했다. AbortError를 삼키지 않고 다음 MR로 넘어가지 않는다.

운영 녹음·MR·분석을 읽거나 일괄 재분석하지 않았다. DB·기존 저장·history 정책은 변경하지 않았다.

## 합성 음원 측정

### 파일 로딩 복구 추가 검증

제공된 숫자 진단에서는 비교 녹음의 파일 조회·다운로드가 307.8초, MR 로딩이 103.5초 후 실패였고 MR 차감은 실행되지 않았다. 이 결과를 계산 속도 문제로 간주하지 않는다. 원본 진단 파일이나 운영 음원은 저장소에 넣지 않았다.

- 보컬 분석과 소리 길 화면에서 같은 읽기 전용 로더를 사용한다. 주소 조회는 15초, 바이트 수신 정지는 20초로 제한하고 일시적 오류·만료된 주소는 한 번 새 주소로 재시도한다. 두 시도를 합친 파일 읽기는 최대 10분, 디코딩·MR mono worker 응답은 30초로 제한한다. 바이트가 계속 들어오면 수신 정지 타이머를 갱신하지만 전체 10분 제한은 적용된다. 한도를 넘으면 부분 파일을 분석하지 않고 안내 후 중단한다.
- R2 주소 재발급은 기존 캐시를 우회하고 분석의 중단 신호를 전달한다. 일반 재생의 주소 캐시·동시 요청 공유는 유지한다. 기기에 원본이 있으면 계속 그 파일을 우선한다.
- 파일 주소 조회·본문 수신·디코딩 중에도 그만하기/화면 이탈은 즉시 대기를 끝낸다. 재시도 전에 부분 바이트를 버리고 새 응답 전체를 받는다.
- 연결 실패를 키·빠르기 불일치로 설명하지 않는다. 실패 후 계속 남던 `재는 중` 표지를 `아직 못 잼`으로 바꾸고 오류 안내를 재시도 버튼 위로 올린다. 이미 잰 쪽의 결과는 유지하며 다음 실행은 못 잰 쪽만 처리한다.
- 실패한 단계·HTTP 상태·시도 횟수·받은 바이트 수를 진단에 추가한다. 양쪽 분석이 완료되지 못해도 진단을 내보낼 수 있다. 주소·토큰·파일 식별자·원문 오류는 포함하지 않는다.

기존 PR 코드에서 만료된 MR 주소의 브라우저 회귀 테스트가 실패하는 것을 확인했고, 수정 후 통과했다. 실패 후 `재는 중`이 남는 문제도 실패 테스트로 확인한 다음 수정했다. 합성 음원 기반 관련 화면 전체 31개 통과(선택한 모바일 프로젝트에서 크기/수동 캡처용 4개 제외), 오류 표시 수정 후 관련 7개 재검사 통과. 모델·로더·분리 관련 Node 전체 61개 통과 후 이전 Safari의 abort 사유 처리와 녹음 파일 주소 갱신 테스트를 추가해 해당 13개 재검사 통과. 로컬 JS 구문 검사 통과. 375×812와 320×640 오류 화면 전후를 로컬 산출물에 저장했다.

실제 통신망 속도가 빨라졌거나, 제공된 녹음의 실제 iPhone 실행이 짧아졌다고 주장하지 않는다. 운영 파일 재분석·서버 데이터 변경·배포는 수행하지 않았다. 기존 PR에 최신 main의 녹음별 MR 선택 기능을 함께 반영한다.

Windows / Node 26.13.0, 8 kHz mono, MR이 목소리보다 8 dB 큰 합성 녹음. 비교 기준은 main `0b96adb`의 `app/mr-cancel.js`이다. 아래는 한 번의 실행 예이며, 시간은 다른 작업의 부하에 따라 크게 달랐다.

| 녹음 길이 | 차감 시간 전 → 후 | 프로세스 최대 메모리 전 → 후 |
|---|---|---|
| 20초 | 0.521 → 0.479초 | 97.8 → 83.3 MiB |
| 3분 | 1.247 → 1.360초 | 212.7 → 110.9 MiB |
| 10분 | 4.450 → 4.435초 | 554.8 → 206.2 MiB |

**순수 계산 시간의 유의미한 개선은 입증하지 않았다.** 개선 효과는 긴 녹음의 메모리 사용 감소(10분 예에서 약 63%), 배치의 반복 다운로드·디코딩 제거, 계산 중 진행 표시다. 메모리는 합성 음원 생성까지 포함한 프로세스 최고치이며 브라우저 탭/iPhone 수치가 아니다. 별도 반복에서 10분은 7.51 → 8.36초로도 측정됐다. 실제 기기의 멈춤 원인을 확정하거나 해소를 검증한 결과로 해석하지 않는다.

20초·3분·10분 모두 이전/이후 음성 전체 SHA-256과 정렬·제거량 보고가 같았다. 예를 들어 10분 결과는 `eae2bd9899cfc120ea1afe9eaf0e1e3a253a9648152c542105852966b212af2e`였다.

재현 명령(각 모듈을 별도 프로세스에서 실행):

```sh
git show 0b96adb:app/mr-cancel.js > mr-before.cjs
node tools/bench-mr-cancel.cjs ./mr-before.cjs 600
node tools/bench-mr-cancel.cjs ./app/mr-cancel.js 600
```

## 자동 검증

먼저 이전 코드에서 진행률 누락, MR 중복 다운로드, URL 조회 중 중단 후 다운로드를 실패 테스트로 확인했다.

- 모델·분리·중단/캐시 관련 Node 테스트 통과. 합성 노래, 속도 차이 ±0.5%, 다른 MR 거절, 원본 보존, 블록 경계·패딩 끝부분을 포함한다.
- 3분 차감의 Float64 작업 배열이 512칸 이하이고 전체 작업 할당이 8 MiB 미만인지 회귀 테스트한다.
- 캐시가 worker로 전송된 후에도 다음 녹음에서 정상이며 24 MiB 이하로 제한되는지 검사한다.
- Chromium 모바일 화면 전체 초기 검사 24개 통과 / 크기별 선택 검사 3개 제외. 최종 변경 후 MR 실분석·여러 녹음 처리·중단·raw bytes 보관·320px 관련 화면 재검사 8개 통과.
- 실제 분석 browser 테스트는 2개 녹음에서 MR 다운로드가 1회이며, 차감 중 실제 진행률이 여러 번 전달되는지 확인한다. 기존 분석 history 보존과 다른 MR일 때 기존 결과 유지도 확인한다.
- 새 회귀 테스트는 `Vocal lab screens checks`에 포함한다. 로컬 JavaScript 구문 검사 통과.

화면 검사는 Chrome의 모바일 크기 모의 실행이다. 실제 iPhone Safari와 운영 파일의 장시간 다운로드·실제 멈춤 재현은 미검증이다. PR만 제출하고 병합·배포하지 않는다.
