# 아이폰 업로드 메모리 개선과 검증

기준 PR #8: 030233590d99d9435f460409ae37f45c5bb944e7.

## 확인한 경로

보관함의 클라우드 가져오기는 원본을 TUS로 전송하지만, 연습 폼은 파일 크기와 관계없이 길이를 디코딩하고 전체 ArrayBuffer를 만들어 IndexedDB에 저장했습니다. FileList를 배열로 바꾸는 것은 파일 바이트 복사가 아니라 참조 복사입니다. 실제 큰 메모리 할당 지점은 전체 파일 arrayBuffer()와 Blob 생성입니다.

## 변경

- 보관함과 연습 모두 한 번에 파일 하나를 선택합니다. 파일 확장자와 MIME을 명시하며 m4v/빈 MIME 추론도 유지합니다.
- 25MB 이하의 연습 가져오기는 기존 기기 저장을 유지합니다. 25MB 초과 가져오기는 로그인 후 원본을 TUS로 직접 전송합니다.
- 큰 연습 파일은 로컬 저장/전체 파일 읽기/미리보기 디코딩 없이 전송합니다. 길이가 없으면 시간을 직접 입력하도록 안내합니다.
- 크기·유형·로그인 검사를 전송 전에 수행하며 최대 500MB를 넘으면 즉시 거부합니다. 25MB는 로컬 복사 비용을 줄이기 위해 택한 기준으로, 실기기 한계를 측정한 수치는 아닙니다.
- TUS 세션 생성과 전송을 분리하고 Supabase의 6MiB 청크 설정을 유지합니다. 전체 가져오기 작업은 한 번에 하나만 허용합니다.
- AbortSignal을 통해 두 화면에서 전송을 취소하고 pagehide에서도 중단합니다. 성공/실패/취소 후 입력 잠금과 파일 참조를 해제합니다.
- 보관함 metadata 등록까지 성공해야 연습 mediaIds에 연결합니다. 전송 후 metadata 등록 단계에는 취소 버튼을 숨깁니다.
- 메타데이터는 업로드를 시작한 계정으로 연결하고 중간 계정 변경을 확인합니다.
- 브라우저 압축은 호출하지 않습니다. 기존 video-optimizer.js 파일은 삭제하지 않습니다.

## 자동 검사 범위

큰 파일은 실제 대용량을 할당하지 않는 File.size 대역을 사용합니다. 전체 파일 arrayBuffer와 큰 파일 createObjectURL 호출 시 실패하도록 감시합니다. 실제 메모리 사용량 측정이나 실기기 미디어 디코딩 검증은 아닙니다.

추가 시나리오:
1. 큰 연습 파일의 직접 전송·원본 포맷·청크 설정·metadata 등록 후 연결.
2. 전송 취소, transport abort, 입력 초기화, 다음 업로드 가능.
3. 전송 실패 시 연결 없음과 재선택 성공.
4. 보관함/연습 동시 전송 방지와 취소 후 잠금 해제.
5. 500MB 초과 사전 거부와 복사/디코딩/업로드 미호출.
6. 비로그인 큰 파일 거부와 기존 작성 내용 유지.

기존 녹음·녹화·작은 파일 저장·재접속·보관함·날짜 입력 검사를 함께 실행합니다. 결과는 PR #8의 SHA별 Checks에 기록합니다.

## 아직 검증하지 못한 것

- 실제 iPhone Safari의 사진 선택기, HEVC/MOV 원본, 25~500MB 전송 중 메모리 사용량과 앱 종료 여부.
- 실제 Supabase 계정/Storage 정책/서버 용량 제한과 재시도.
- 앱을 백그라운드로 전환하거나 잠금/네트워크 변경 시 OS 동작.
- 페이지 종료 후 이전 전송을 이어 올리는 기능. 취소 후에는 원본을 다시 선택해야 합니다.
- 기존 대용량 로컬 파일 전체 조회와 장시간 직접 녹화의 메모리 관리. 이번 변경은 가져오기 경로를 대상으로 합니다.
- 실패한 업로드 세션/metadata 등록 전 파일의 서버 측 정리 정책.

따라서 '아이폰 크래시 해결 완료'로 표시하지 않습니다.
