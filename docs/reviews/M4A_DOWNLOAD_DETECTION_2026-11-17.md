# 형식 정보가 없는 M4A 다운로드 보완

PR #450은 이름에 남은 `.bin`을 정리했지만, 형식 정보 자체가 없는 녹음은 여전히 일반 바이너리로 분류했다. 후속 사용자 파일은 내부적으로 명시적인 M4A 컨테이너였고 원본 바이트는 정상이었다. 파일·파일명·음성·파형은 저장소에 포함하지 않았다.

## 변경

`VZ.media.download` 안에서 로컬 파일 앞부분(최대 64바이트)과 기존 클라우드 준비 과정에서 이미 받은 바이트의 명시적인 `ftyp`/`M4A ` 표지를 확인한다. M4A로 확인되면 다운로드 사본에 `.m4a`와 `audio/mp4`를 함께 사용한다. 일반 MP4의 `isom` 표지만으로는 M4A로 판단하지 않는다. 다른 파일의 기존 형식 처리는 유지한다.

기존 제한·재시도 읽기와 사용자 계정/세션 확인, MR 원본 파일명 옵션, 중복 확장자 정리, 길이 제한을 재사용한다. 원본 바이트·서버 메타데이터·저장 제목·DB는 바꾸지 않는다. 클라우드 바이트 확인은 기존 200MB 이하 다운로드 준비 범위에 적용되며, 그보다 큰 파일은 기존 네이티브 저장 경로를 유지한다.

## 검증

- 가짜 M4A 헤더와 형식 정보 없는 `.bin` 항목으로 실패 테스트 두 개(로컬/클라우드)를 먼저 재현했다.
- 수정 후 신규 3개와 기존 다운로드 14개를 Chromium 모바일/데스크톱, 자동 WebKit에서 실행해 **51/51 통과**했다.
- 파일명·Blob MIME·다운로드 바이트 일치·원본 데이터 무변경, 일반 MP4 및 알 수 없는 바이트의 오분류 방지를 확인했다. 기존 MR 다운로드·실패 재시도·이탈/계정 격리·404·320/390/430px 회귀도 통과했다.
- 전체 애플리케이션 JS 구문 검사와 `git diff --check` 통과.
- 실제 iPhone Safari는 사용하지 못했다. 실제 기기의 다운로드 확인창·파일 앱 저장/재생은 미검증이다. 이전 PR의 기존 WebKit 키 변경 재생 실패(main에서도 동일)는 이 후속에서 변경하지 않았다.

실제 사용자 음원의 오프라인 반주 분리 작업은 이 코드 수정과 별도이며, 그 음원·모델·출력 파일을 Git에 넣거나 서버로 업로드하지 않았다.
