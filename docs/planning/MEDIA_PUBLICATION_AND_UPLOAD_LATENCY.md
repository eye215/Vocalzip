# 업로드 완료 등록·전송 전 대기 개선

2026-11-10, PR [#233](https://github.com/eye215/Vocalzip/pull/233). Phase 06·08, 저장 유실 방지 선행 작업.

## 구현 범위

- Worker `POST /v2/media/publish`: 업로드가 완료된 UUID 시도별 오디오 원본을 R2 HEAD로 검증한다. 사용자·현재 JWT 세션·원본 키/크기/형식/루트/ETag·요청 ID와 **전체 metadata 해시**를 별도 HMAC 증명에 묶는다.
- SQL `vzip_publish_media`: 현재 등록 세션·revision 모드·root/삭제 가드를 잠금 아래 확인하고 보관함에 **INSERT ONLY**로 등록한다. 같은 ID의 다른 원본/다른 계정 기록은 교체하지 않는다. 동일 원본이 이미 등록되어 있으면 최신 제목·날짜·곡·메모를 그대로 반환한다.
- 최소 publication 영수증은 요청/세션/개체 ID와 metadata 해시만 보존한다. 원본·메모를 별도 원장에 복제하지 않으며 직접 클라이언트 접근은 허용하지 않는다.
- 앱은 고유 업로드 시도 UUID를 안정적인 publication 요청 ID로 사용한다. 완료된 서버 응답을 등록 확인으로 사용하며, 불명확한 응답은 기존 보관함을 다시 확인한다. 실패한 원본/로컬 완료 영수증은 삭제하지 않는다.
- 새로고침 후 원본 File 없이도 기존 완료 영수증으로 서버 등록을 다시 시도한다. 계정/세션 변경 결과는 현재 화면에 연결하지 않는다. 기존 legacy 계정 등록 방식은 유지한다.

## 업로드 시간

현재 v1 전송은 보통 **최대 4개 × 8MiB**, 저사양/느린 연결/데이터 절약 모드는 **2개** 조각을 병렬 전송한다. v2는 현재 2개다. 원본을 재인코딩하거나 샘플레이트/비트레이트를 바꾸지 않는다.

이번에 개선한 것은 파일 전송 전/후 대기다.

| 구간 | 변경 |
|---|---|
| 사전 확인 | 삭제 여부·기존 보관함 기록·R2 연결의 독립 조회를 함께 시작. 세 결과를 확인하기 전에는 업로드/등록하지 않음 |
| 등록 확인 | revision 서버가 원본과 등록을 확인한 응답을 사용해 성공 시 별도 보관함 재조회 한 번을 생략 |
| 완료 후 재시도 | 저장된 영수증과 불변 원본을 다시 연결. 원본 파일 재선택/재전송 없이 복구 |
| 기존 전송 | 병렬 수/조각 크기/바이트·음질 유지 |

동일 지연의 합성 네트워크에서 새 파일이 전송을 시작하기까지의 사전 조회 대기를 기준 main과 비교한다. 기능 SHA `e5b180abf46745b7c12fffe992525a86356ad033`의 [실행 42778180522](https://github.com/eye215/Vocalzip/actions/runs/42778180522)에서 요청당 30ms 합성 지연을 적용했을 때 **90ms → 31ms**였다. 클라이언트 9개, SQL/workerd/R2 22개, 기존 rollout DB 22개도 통과했다. 브라우저/다른 회귀 결과는 PR에 기록한다. 이 수치를 실제 사용자 전체 업로드 시간·이동통신 속도 개선율로 확대하지 않는다.

사진 앱/iCloud가 파일을 준비하여 웹앱에 넘기기 **이전** 시간은 웹 코드로 강제 단축할 수 없다. 이전 #208의 음성 패킷 재사용을 유지한다. 원본 크기와 회선 업로드 대역폭이 실제 전송 시간의 하한을 결정한다. iPhone에서는 파일 선택 전후·음원 준비·전송·등록을 나누어 측정해야 한다.

## 검사와 한계

- 신규 클라이언트 계약: 서버 확인, 요청 재사용, 다른 계정/세션, 위조 응답, legacy/paused, 독립 조회 동시 실행과 삭제/계정 변경 거부.
- 격리 PG + 실제 workerd/메모리 R2: 신규 등록·재실행·수정 보존, HMAC에 전체 입력 바인딩, 다른 원본/계정 ID 충돌, 삭제/정지/회수 세션, legacy 경로·부정 metadata 차단. 기존 삭제 계약과 함께 검사.
- 브라우저: 실제 앱 업로드→서버 등록 경로, 직접 metadata upsert 생략, 잘못된 응답의 영수증/원본 보존, 새로고침 후 재전송 없는 복구.
- 기존 이어올리기/보관함 복구/업로드/스냅샷/정산 회귀 검사를 실행하며 실제 결과는 PR과 실행 현황에 기록한다.

**운영 Supabase PostgREST/Vault·Cloudflare R2·iPhone/두 실기기 검사는 별도다.**

## 아직 활성화하면 안 되는 이유

`20261117_media_publication.sql`은 **proposals 전용**이다. 운영 Worker 배포/SQL 설치/계정 전환·원본 변경을 하지 않는다. `MEDIA_VERSION_GUARD_ENABLED=false`, `UPLOADS_V2_ENABLED=false`, 새 동기화 OFF를 유지한다. 현재 운영의 legacy 경로에는 사전 조회 병렬화가 적용될 수 있지만 새 등록 RPC는 서버가 revision 모드를 알린 경우에만 사용한다.

이 PR은 **신규/미등록 완료 원본 게시**만 연결한다. 원본을 바꾸는 교체 업로드나 기존 곡명/날짜/제목 편집용 revision metadata CAS RPC는 아직 추가하지 않았다. 구형 수정 DML이 전환 계정에서 차단되는 문제는 후속이다.

남은 순서:
1. metadata 편집 CAS 및 삭제 prepare/commit 앱 연결.
2. 고정 키·legacyStorage·PDF·공연 자료/영상, 다른 서버 writer의 호환/인수. 기존 파일 자동 이동·삭제 금지.
3. 복구 입력·최소 영수증 보존/정리와 용량 정책, 운영 HTTP·진행 중 구형 작업 소진·두 기기/iPhone 검사.
4. 소유자 계정부터 제한 활성화.

[서버 원본 보호 선행 계약](STUDENT_1_0_MEDIA_VERSION_SERVER.md)의 나머지 게이트를 이 PR이 해제한 것으로 표시하지 않는다.
