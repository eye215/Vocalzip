## 재현한 오류와 이번 수정

시간당 레슨비 저장은 `hourlyRate`와 `settings/hourly-rate.save` 변경 이력을 생성한다. 그러나 `billing/backup.js`는 둘 다 허용하지 않아 **정상적으로 저장한 정산의 JSON 복원·클라우드 업로드/다운로드가 차단**된다.

재현: `C.reduce(C.empty('device'), {type:'hourly-rate.save', payload:{hourlyRate:50000}})` 결과를 `B.validate`에 전달하면 `알 수 없는 최상위 필드: hourlyRate` 오류가 난다. 필드만 허용해도 settings 이력 검사에서 다시 거부되므로 둘을 함께 검증해야 한다.

또한 백업·클라우드 미리보기는 여전히 계약 횟수 기준 잔여/미납을 표시한다. 실제 입금 20만원, 시간당 5만원, 2시간 수강이면 잔여는 2시간인데, 10회·30만원 레슨권 기준 계산은 8회/미납 10만원을 표시한다.

변경 범위:

- `billing/backup.js`: 양의 원 단위 hourlyRate, 해당 설정 변경 이력 검증. 시간 기준 미리보기는 기존 `C.hourlyTotals`를 사용한다. 기존 횟수 백업과 알 수 없는 필드·중복 차감 차단은 유지한다.
- `billing/transfer.js`: 미리보기 단위를 시간/회에 맞춰 표시한다. 레이아웃이나 전송 프로토콜은 변경하지 않는다.
- `billing/tests/hourly-backup.test.cjs`, `billing/tests/hourly-backup.spec.cjs`: JSON 파일 다운로드/복원, 교체 전 기록 복구, 클라우드 전송 대역, 새로고침, 잘못된 설정·이력 검증.
- 이 문서. 기존 정산 계산식·CSV 매핑·앱 화면·공통 CI 변경 없음.

최종 SHA와 실제 테스트 결과는 이 문서가 포함된 PR에 기록한다. 브라우저 클라우드 검사는 모의 인증/API이며 실제 계정 검증과 구분한다.

## 추가로 발견한 운영 위험 — 재현 오류와 구분

1. **일반 앱 동기화의 서버 동시 저장**: `cloud-sync.js`는 서버를 읽고 ID별로 병합한 뒤 `vocal_data.upsert`한다. 정산 RPC와 같은 서버 버전 비교가 없다. 두 기기가 같은 과거 값을 읽고 각각 저장하면 마지막 서버 스냅샷에서 상대 기기의 새 기록이 빠질 수 있는 경로다. 코드 분석 결과이며 실제 계정 동시 쓰기는 아직 재현하지 않았다. 기존 병합/삭제 표식 기능은 유지하며 별도 개선해야 한다.
2. **R2 이전 시 원본 확보**: `app/storage.js:moveOne`은 먼저 `vzipCloudMediaBlob`으로 전체 Blob을 확보한 뒤 R2에 올린다. R2 업로드 자체는 8MiB 이하 조각을 순차 전송하지만, 원본을 얻는 단계의 메모리 상한까지 증명하지는 않는다. 실제 큰 파일과 iPhone 측정이 필요하다. 크기 비교만으로 바이트 내용까지 동일하다고 단정하지 않는다.
3. **계속 업로드와 이어받기는 다름**: R2 클라이언트는 전송 중 조각 재시도가 있지만, 페이지를 닫은 뒤 같은 multipart 작업을 영속적으로 재개하는지는 별도 검증 대상이다.
4. **문서의 기준 버전 차이**: 기존 인수인계서는 v5.6이며 지금은 v6 파일 구조다. 녹화/영상 처리 요구도 후속 변경으로 음원 추출 중심이 됐다. 옛 문서만 보고 기능을 다시 만들지 않는다.

## 운영 정산 DB 확인 결과

프로젝트 `chxnbtiyuyhiywzeshis`에 `vocal_billing_documents`와 `vocal_billing_save`가 존재한다. 이번 읽기 전용 점검 결과:

- 테이블 RLS 활성화.
- authenticated는 SELECT만 가능하며 INSERT/UPDATE/DELETE 직접 권한 없음.
- anon SELECT와 RPC 실행 권한 없음.
- SELECT 정책은 `auth.uid() = user_id`.
- 저장 RPC는 authenticated만 실행 가능하며 빈 search_path, auth.uid() 소유자 검사, 서버 revision 비교 구조다.
- 이전 작업에서 마이그레이션 적용과 임시 PostgreSQL의 권한/동시 쓰기 테스트가 완료됐고, 이후 main에 관련 코드가 병합됐다. `docs/운영검증_2026-11-04.md`의 “접근 권한 때문에 확인 대기”는 그때 연결 상태에 대한 기록이며, 현재 조회 결과와 구분해야 한다.
- 서버 스냅샷의 실제 사용자 데이터는 조회·수정하지 않았다. 이 점검을 실제 로그인 브라우저에서의 성공으로 보고하지 않는다.

보안 권고에는 인증 사용자가 SECURITY DEFINER RPC를 실행할 수 있다는 경고가 있다. 이는 직접 테이블 쓰기를 막고 본인 저장 RPC만 제공하기 위한 의도된 경계이며 auth.uid()/권한/고정 경로를 검토했다. [권고 설명](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable).
기존 Auth의 유출 비밀번호 보호 비활성 경고도 남아 있으며 이번 정산/충돌 점검에서 인증 설정은 바꾸지 않았다. [설정 안내](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

실제 iPhone Safari, 실제 계정의 양방향 클라우드 전송, 실제 R2 대용량 파일 이동은 별도 검증 전까지 완료로 표시하지 않는다.
