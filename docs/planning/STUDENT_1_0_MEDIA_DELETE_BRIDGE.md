# Phase 03·05 — 미디어 삭제의 저장 계약 연결

작성: 2026-11-10. #214 후속. 새 동기화는 기본 OFF이며 운영 DB/계정 전환·기존 파일 변경은 수행하지 않는다.

## 구현 범위

- revision 경로는 계정/세션에 묶인 작은 삭제 의도를 먼저 보존한다. 파일 바이트·메모 본문·토큰을 복제하지 않는다.
- root snapshot의 삭제 표시와 곡/레슨/연습의 선택 파일 참조 정리를 revision RPC로 확인한 뒤 원본 정리를 시작한다. 이전 직접 INSERT/UPDATE 경로로 우회하지 않는다.
- 미완료 RPC는 같은 파일·메타데이터 지문에 해당하는 삭제 요청만 같은 ID로 확인한다. 일반 저장이나 다른 파일의 pending을 삭제 성공으로 간주하지 않는다.
- 메타데이터와 서버 버전의 SHA256 지문을 다시 확인한다. 알려진 변경·저장 실패·계정/세션 변경은 원본 정리 전에 중단한다.
- 원본/메타데이터 정리가 끝나도 로컬 파일 정리까지 성공해야 삭제 의도를 해제한다. 같은 Auth 세션의 새로고침/재접속은 이미 확인한 삭제 의도를 재개하며, 새 로그인 세션은 자동 실행하지 않는다.
- pending snapshot의 선택 미디어 참조만 정리하고 다른 레슨 메모·연습 시간·선택하지 않은 파일은 보존한다.
- 기본 OFF이며 기존 프로토콜 상태/삭제 의도가 없는 계정의 기존 삭제 경로는 유지한다. 기존 프로토콜 상태나 의도가 있는 계정을 자동 legacy로 되돌리지 않는다.

## 검사

실행한 결과만 PR에 추가한다. 모델/전체 root 스크립트/실제 앱 브라우저/임시 PostgreSQL을 구분한다. 실제 Supabase HTTP·R2 운영 삭제·iPhone 실기기 인수로 자동 시험을 대신 표시하지 않는다.

## 남은 인수 조건

- 충돌·이전 로그인 삭제 의도의 명시적 확인 화면은 후속 작업이다. UI 디자인은 수정하지 않는다.
- R2의 같은 key에 대한 다른 writer와 삭제 사이의 원자적 개체 버전 보호 및 기존 클라이언트 서버 차단은 별도 서버 인수 대상이다. 클라이언트의 메타데이터 재확인만으로 원자성을 주장하지 않는다.
- 기존 복구 사본/전사 데이터 보관 정책, 실제 R2/Supabase 및 iPhone 중단·재로그인·두 기기 인수는 남아 있다.
- 운영 활성화는 전체 저장/삭제 경로와 복구 흐름을 검증한 뒤 별도로 진행한다.

추가 확인한 경계:
- 일반 저장 pending을 파일 삭제 영수증으로 처리하지 않음.
- 손상된 로컬 JSON/레코드를 클라우드 복사본으로 교체한 뒤 삭제하지 않고 원본을 보존하며 중단.
- 삭제 도중 계정이 바뀌면 다른 계정 DB의 같은 ID 파일을 지우지 않음(실제 브라우저 IndexedDB 사례).
- 파일별 완료 확인 잠금은 다른 파일 업로드가 끝날 때까지 기다리지 않도록 분리.
- 기존 삭제 단위 검사의 이벤트/저장소 모형을 브라우저 API에 맞게 보완했고, 원본 삭제·참조 정리·실패 재시도 검사는 유지했다.
