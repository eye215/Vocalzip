# Phase 03·05 이전 로그인에서 중단된 파일 삭제 재개

[#231](https://github.com/eye215/Vocalzip/pull/231), 기준 main `3e62b954ec473387b74c40153e8e4cc482b24808`. 새 동기화 **기본 OFF**, 운영 SQL/계정 활성화/실제 미디어 변경 없음.

## 연결한 범위

- 설정의 중단된 삭제 목록은 현재 계정의 intent만 조회하고 현재 서버/기기 이름을 표시한다. 20개 단위로 읽고 파일을 하나 선택하면 기존 전체 비교 페이지를 재사용한다.
- 파일명·영구 삭제/복구 불가·레슨/메모/실제 연습 시간 보존을 안내한다. 달라진 기록 선택과 마지막 체크를 마쳐야 현재 세션의 새 root CAS를 전송한다.
- `reviewMediaRecovery(context)`는 해당 owner/id/원래 metadata stamp의 sidecar에 묶인 별도 capability다. 일반 복구의 물리 삭제 차단은 유지한다. 같은 파일의 삭제 pending 또는 일반 미전송 pending은 내용을 함께 비교하고 보존할 수 있지만, 다른 파일의 삭제 purpose를 인계하지 않는다.
- 기존 로그인 요청 ID는 재사용하지 않는다. 이전 pending과 입력은 삭제 대상 파일 링크를 정리해 보존한다. 현재 서버 revision/generation과 로컬/journal/intent를 다시 확인한 새 CAS의 ACK 이후에만 sidecar를 현재 로그인으로 인계한다. 출처 로그인은 root 복구 메타데이터에 기록한다.
- ACK 유실 시 sidecar는 이전 로그인에 남는다. 사용자 결과 확인은 같은 새 요청으로 재시도하고, 확인되지 않으면 원본 정리로 진행하지 않는다. ACK 뒤 sidecar 인계 전에 종료되면 다음 진입에서 다시 명시적으로 확인한다.
- 파일 메타데이터가 바뀌거나, 정리 완료 후 메타데이터가 다시 생겼거나, 계정/세션/기록이 바뀌면 추가 물리 삭제를 멈춘다.
- 클라우드 완료 뒤 기존 미디어 삭제 경로로 기기 파일·연결을 정리하고 로컬 완료 ACK 뒤 intent를 해제한다. 해당 파일 이외의 원본과 메모/시간은 보존한다.

## 기기 파일 보호

현재 `vzipStorePracticeMedia`로 파일 내용을 쓰는 경로는 로컬 `localRevision`을 새로 부여한다. 오디오 바이트를 복제·압축하지 않는다. 기존 파일에 일괄 backfill은 하지 않는다.

파일 확인은 로컬 metadata/저장 revision 및 Blob 크기·형식의 토큰을 사용하고, 그 SHA-256만 intent의 `localStamp`에 보존한다. 원본 바이트를 전부 읽거나 토큰 원문을 서버/로그에 올리지 않는다. 삭제 확인 전/서버 ACK 후/정리 직전에 비교하며, IDB 내 read→조건 검사→delete도 한 readwrite transaction에서 수행한다.

다른 탭의 저장으로 로컬 파일이 바뀌면, 현재 시도뿐 아니라 같은 intent의 자동 재개에서도 새 기기 원본을 지우지 않는다. 클라우드 원본이 이미 정리된 상태에서 기기 버전이 바뀌었다면 새 기기 파일을 보존하고 별도 확인을 기다린다.

**이것은 원본 바이트 전체 해시나 R2 원자적 개체 버전 보장이 아니다.** 예전 캐시된 작성자가 로컬 revision을 유지한 채 같은 metadata/크기·형식으로 바이트를 바꾸는 경로까지 보장하지 않는다. 활성화 전 구 클라이언트/로컬 writer 인수와 서버 원본 버전 보호를 완료해야 한다.

## 검증 및 한계

합성 SDK/REST·브라우저와 격리 PostgreSQL을 사용한다. 실제 SHA/결과·CI의 기존 실패/설치 재시도·배포 확인은 #231에 기록한다. 격리 DB의 media fixture에는 최소 owner RLS와 select/delete 권한을 모델링하며 기존 세션 제한을 함께 적용한다. 운영 권한/스키마를 바꾸지 않는다.

R2 실제 개체, 운영 Supabase HTTP/JWT, iPhone 앱 종료/잠금·두 실제 기기 검증은 수행하지 않았다. 기본 OFF 상태의 소스 구현과 운영 인수는 구분한다.
