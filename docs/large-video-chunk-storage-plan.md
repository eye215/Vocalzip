# 200MB 영상 분할 저장 구현 계획 (Issue #14)

## 현재 코드에서 확인한 차단
- `media-hub.js`: 50MiB 초과 파일을 사전 거부한다.
- `cloud-sync.js`: TUS 업로드 시작 전에 50MiB 초과를 거부한다.
- TUS의 6MiB 네트워크 청크는 최종적으로 **단일 Storage 객체**가 되므로 파일당 50MB 제한을 해결하지 않는다.

## 구현 원칙
- 1인용/무료 플랜 유지, 기존 데이터와 50MB 이하 업로드 경로는 그대로 둔다.
- 200MB 파일은 40MiB 이하 크기의 별도 Storage 객체로 분할 저장한다. 원본 전체를 메모리에 올리지 않는다.
- manifest에 `version`, `mediaId`, `ownerId`, `name`, `mime`, `size`, `chunkSize`, `parts: [{index,path,size}]`, `state`를 저장한다.
- 모든 조각이 업로드되고 검증되기 전까지 보관함의 정상 파일로 등록하지 않는다.
- 업로드 재시도 시 해당 사용자/미디어의 성공 조각을 재사용하고, 실패한 조각만 재전송한다.
- 취소/삭제 시 조각·manifest·메타데이터를 정리한다. 실패 시 안전한 복구 경로를 남긴다.

## 재생 기술 검증 선행 (중요)
- MP4/MOV 원본을 임의 바이트로 자른 조각은 각각 재생 가능한 영상이 아니다.
- 브라우저에서 모든 조각을 Blob으로 합치면 iPhone 메모리 문제가 재발한다.
- 인증된 HTTP Range 응답으로 원본 바이트를 이어주는 스트리밍 계층이 필요하다. Edge Function의 응답 크기·시간·대역폭·Range 처리 제약을 **실제 운영 환경에서 먼저 확인**한다.
- 해당 경로가 불가능하면 MP4 컨테이너에 맞는 HLS 세그먼트 생성 및 iOS Safari 호환성을 검토한다. 단순 바이트 조각을 video.src로 넘기지 않는다.

## 단계별 작업
1. 분할 저장 manifest/Storage API/재시도/정리 및 단위 테스트.
2. 인증·Range 스트리밍 경로와 iPhone 재생/seek 검증.
3. `cloud-sync.js`와 `media-hub.js`에서 50MiB 초과 업로드 경로 연결.
4. 연습 폼, 보관함, 삭제, 백업/복원, 다른 기기 재생 통합.
5. 200MB MOV/MP4 실제 아이폰 실기기 QA 후 main 병합.

## 검증 게이트
- 기존 테스트 전체 통과.
- 200MB 업로드 후 새로고침/재로그인/seek/삭제 성공.
- 원본 해시 및 파일 크기 보존.
- 기존 50MB 이하 파일과 레슨·숙제 데이터 회귀 없음.
- 실제 Supabase Free 플랜 제한과 iOS Safari 검증 전에는 배포하지 않는다.

이 문서는 구현 계획이며, 동작하는 200MB 업로드 기능이 아니다.
