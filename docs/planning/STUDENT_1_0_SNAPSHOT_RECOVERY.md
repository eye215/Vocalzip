# Phase 03·05 충돌·이전 로그인 복구 계약

기준 main: `80703914ed1bd56623731c17d1438324dd3b3e18`. 새 동기화는 계속 **기본 OFF**다. 운영 SQL 설치·계정 전환·실제 파일 변경 없이, 기존 transport에 명시적 복구 계약을 추가한다.

## 이번 범위

- `create({getLocal,...})`에 동기식 현재 계정 로컬 조회를 주입한다.
- `reviewRecovery()`: 현재 기기/최신 서버/이전 pending/기존 복구 입력을 독립 복사로 반환한다. 서버 쓰기·로컬 본문 교체·pending 해제는 하지 않는다. 삭제된 레슨/파일의 pending·보존 입력은 기존 삭제 계약에 따라 먼저 정리할 수 있다.
- 반환한 `reviewId`는 해당 인스턴스·로그인에서만 유효하다. 새 조회가 이전 조회를 대체한다. 토큰·비밀키는 저장하거나 반환하지 않는다.
- `resolveRecovery(reviewId, candidate, {confirmed:true})`: 화면에서 충돌 필드별 값을 보여주고 사용자가 승인한 복구안만 전달하는 계약이다. **화면/버튼은 이번에 연결하지 않는다.** 명시적 확인 없음, 로컬/서버/journal 변경, 계정/세션 변경은 전송 전에 거부한다.
- 어느 입력에만 존재하던 ID 기반 레코드도 삭제 표시 없이 빼면 거부한다. 복구를 이용한 새 삭제는 허용하지 않는다. 동일 레코드 안 값은 자동 LWW로 결정하지 않으며 화면에서 선택해야 한다.
- 이전 pending·기기·서버 입력과 새 요청을 계정별 단일 journal에 먼저 원자적으로 보존한다. quota 실패 시 서버 전송 없이 기존 journal을 유지한다. 삭제 복구용 휴지통이 아니라 아직 확인되지 않은 편집 입력이며, 레슨/파일 직접 삭제 시 보존 입력도 함께 정리한다.
- 이전 로그인 요청 ID는 재사용하지 않는다. 현재 로그인 새 ID + 최신 서버 revision/generation CAS로 확인한다. 클라우드 값을 그대로 선택해도 CAS 쓰기를 수행하여 과거 in-flight 요청과 경합한다. 경합 패배 시 재확인하며 자동 재시도/무조건 덮어쓰기를 하지 않는다.
- 저장 응답이 유실되면 같은 새 요청으로만 영수증을 확인한다. 실제 서버가 다음 버전으로 진행했거나, 저장 중 새 로컬 입력이 생기면 양쪽을 유지하고 재확인한다.
- 성공 후 `onAck(row,payload,{recovery})`를 동기식 호출한다. 복구 입력의 로컬 SHA-256이 달라지면 호출하지 않는다. 앱 연결 시 승인한 값을 적용하고 다른 계정의 로컬 보관함 임시 데이터를 보존하는 처리가 필요하다.
- 미디어 삭제 purpose/sidecar는 별도 원본 삭제 증명을 가지므로 일반 복구로 승인하지 않는다. generation 교체도 이 확인만으로 복구하지 않는다.

## 보존/권한 제한

journal은 기존 계정 격리 저장소와 owner/session guard를 사용한다. 서버에는 기존 4개 RPC 인자만 전송한다. 복구 확인 데이터는 서버 history 새 테이블에 복제하지 않는다. 최대 journal 기본 2MiB이며 복구 입력 누적으로 넘으면 보존에 실패했다는 오류로 멈춘다. 임의 자동 만료/정리/로그 출력은 없다.

새 UI 연결 전 결정할 항목: 확인된 복구 입력의 명시적 정리/보존 정책과 용량 UX, 모든 컬렉션 삭제 및 클라우드 history/STT 보존 정책. 현재 레슨/파일 redaction 범위를 다른 데이터 직접 삭제까지 완료했다고 간주하지 않는다.

## 검증

실행 결과는 PR 및 실행 현황에 별도로 기록한다. 검사는 합성 계정·메모리 서버와 격리 PostgreSQL을 사용한다. 통과 전 완료 수치를 기재하지 않는다. 실제 PostgREST/JWT/RLS·운영 R2·두 iPhone 인수가 아니다.
